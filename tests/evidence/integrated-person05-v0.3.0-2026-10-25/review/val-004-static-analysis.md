# VAL-004 静态分析：旧调试快照显示了编辑稿断点集合

- 复核基线：`integration-v0.3.0`，`fff15bee97ed47cf2485b83c4344a020e9e190f7`。
- 复核范围：只读检查 UI 显示与会话控制器；没有修改产品、测试实现或原始证据。
- 证据性质：本文是源码复核。下面的动态现象由主任务提供，浏览器实测记录由主任务另存；本文不声称完成独立动态复现。
- 建议归属与级别：4 号 UI，P2，缺陷编号 VAL-004。

## 已观察现象与源码原因

主任务观察到：在一个已设置断点的会话暂停后，修改源码并移除编辑稿断点，再选择“查看调试快照”，断点列表显示“尚未设置断点”；随后继续执行仍命中旧会话断点。

这两个集合在修改源码后可以合理地不同，但当前 UI 仍用编辑稿集合决定旧快照中的断点列表和行号标记，导致显示与旧会话实际行为不一致。

| 位置 | 已复核代码行为 | 对现象的解释 |
| --- | --- | --- |
| `ui/src/main.mjs:13` | 全局 `requested` 保存当前编辑稿的断点请求。 | 编辑稿集合没有独立的快照显示版本。 |
| `ui/src/main.mjs:28` | `unchanged(snapshot)` 比较快照与当前编辑稿的 `sourceHash`。 | 修改源码后返回 false。 |
| `ui/src/main.mjs:217`、`:218` | `toggleBreakpoint` 直接从 `requested` 删除或加入条目。 | 移除编辑稿断点后，该条目立即从 UI 的循环来源消失。 |
| `ui/src/main.mjs:219` | 只有 `unchanged(activeSnapshot)` 且会话允许设置断点时，才调用 `controller.setBreakpoints`。 | 已修改的编辑稿断点不会发送到旧会话；旧会话保留原绑定是当前快照隔离逻辑的结果。 |
| `ui/src/session-controller.mjs:92` | 匹配会话的 `breakpoints` 事件把实际绑定保存到 `this.view.breakpoints`。 | 控制器仍保存旧会话的权威断点绑定；它与已清空的 `requested` 不同。 |
| `ui/src/main.mjs:80`、`:81` | `renderBreakpoints` 始终遍历 `requested`；即使 `snapshotMode` 为 true，也只为仍在该集合的条目查找 `s.breakpoints` 中的绑定。 | 旧会话绑定存在也无法独立生成列表项。 |
| `ui/src/main.mjs:87` | 空提示完全由 `!requested.length` 决定。 | 在旧快照模式下错误显示“尚未设置断点”。 |
| `ui/src/main.mjs:57` | 行号断点标记始终读取 `requested.some(...)`。 | 旧快照行号上的标记也会随编辑稿删除而消失。 |
| `ui/src/main.mjs:71` | 快照模式明确标为“调试快照 · 只读”。 | 用户会把此时显示的断点理解为旧调试快照的会话状态。 |

`ui/src/session-controller.mjs:164` 至 `:169` 的 `setBreakpoints` 使用当前会话 key，并串行发送命令；此次源码原因定位在 UI 渲染来源。本文没有发现需要以删除旧会话断点来修复此现象的依据。

## 当前显示约定

- `ui/README.md:24` 要求用户能查看请求位置与实际绑定位置；旧快照显示空集合会隐藏仍然有效的绑定。
- `ui/README.md:25` 约定修改后查看只读旧稿，停止并重新编译后才执行新稿。
- `contracts/README.md:24` 区分请求位置与实际绑定位置，且新构建重新绑定。
- `contracts/README.md:27` 要求执行状态以事件或 resync 为准。
- `contracts/README.md:46` 要求编辑稿与活动快照分离。

因此，源码改变后保留旧会话断点符合快照隔离；在旧快照里显示编辑稿的空断点集合违背了上述显示约定。这是断点列表和行号标记的来源错误，不应记录为“继续执行错误地保留断点”。

## 显示侧最小修复建议（未实施）

1. 为断点渲染统一选择数据源：查看当前会话对应的旧调试快照时，使用 `s.breakpoints`，直接展示每条绑定的 `requested`、`status`、`actual` 和 `reason`；编辑稿模式继续使用 `requested`。
2. 行号标记、断点列表和空提示必须使用同一个选定集合，避免只修列表后仍遗漏行号标记。旧快照行号标记按绑定记录的请求位置匹配当前显示文件；实际绑定位置仍在列表中明确列出。
3. 在已修改编辑稿模式中，明确提示这些编辑稿断点于下次编译生效；进入旧快照时展示旧会话绑定。
4. 保留 `main.mjs:219` 对旧会话的隔离，不因编辑稿移除断点而自动发送旧会话删除命令。不得用改动调试后端行为来掩盖显示问题。

建议回归序列：旧会话绑定并暂停 → 修改编辑稿 → 删除编辑稿断点 → 查看旧快照，列表与行号仍显示旧会话断点 → 继续执行并再次命中 → 停止并重新编译编辑稿，确认已删除的断点不再出现在新会话。

本文仅提出最小修复方向；4 号实现后仍需经 1 号集成，再由 5 号对新集成基线复测签收。
